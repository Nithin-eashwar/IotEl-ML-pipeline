# Repository Guidelines

## Project Structure & Module Organization

This repository contains a NILM motor-load classifier and related ESP32 firmware.

- `ml/nilm_pipeline.py`: main Python ML pipeline for loading CSV data, extracting window features, training, evaluating, and writing `ml/model.pkl`.
- `ml/compare_nilm_features.py`: Python comparator — reads an ESP32 JSON window dump and recomputes all 20 features independently.
- `single.py`: standalone Python workflow used alongside the main pipeline.
- `test_azure_connection.py`: Azure IoT Hub connection diagnostic.
- `firmware/esp32_telemetry.c`: production ESP-IDF firmware (FreeRTOS tasks, sensor drivers, NILM inference, Azure MQTT).
- `firmware/nilm_validate_features.c`: standalone ESP32 test firmware — captures one 128-sample window and dumps raw samples + 20 computed features as JSON for desktop comparison.
- `firmware/nilm_model.h` / `firmware/nilm_model.c`: generated C Random Forest export (auto-generated by `export_random_forest_firmware()`).
- `firmware/iot_testbed/`: active Arduino sketch for 100 Hz sensor capture and CSV streaming.
- `firmware/legacy/`: modular ESP32/FreeRTOS firmware with sensor, motor, NILM, calibration, and MQTT components.
- `docs/` and `NILM_Cross_Session_Report.md`: design notes and evaluation report.
- `data/`, `results/`, `*.csv`, `*.png`, `*.pkl`, and `.env` are generated or local-only and must not be committed.

## Build, Test, and Development Commands

Create an environment and install dependencies:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Run the primary evaluation:

```bash
python ml/nilm_pipeline.py
python ml/nilm_pipeline.py --mode loso
```

Check Azure IoT Hub credentials and connectivity:

```bash
python test_azure_connection.py
```

Compile/upload ESP-IDF firmware:

```bash
idf.py set-target esp32
idf.py build && idf.py flash monitor
```

Feature validation workflow:

```bash
# 1. Flash test firmware
cp firmware/nilm_validate_features.c firmware/nilm_model.c firmware/nilm_model.h main/
idf.py build && idf.py flash monitor

# 2. Copy the JSON dump from serial (between === START === and === END === markers)

# 3. Compare
python ml/compare_nilm_features.py esp32_dump.txt
```

## Coding Style & Naming Conventions

Use Python 3.10+ with 4-space indentation, `snake_case` functions and variables, and uppercase constants for pipeline configuration such as `WINDOW_SIZE` and `DATA_DIR`. Keep data-loading, feature-extraction, and evaluation logic separated. Firmware uses C with `.h`/`.c` modules, uppercase `#define` constants, and clear task names such as `vMotorTask` and `vSensorTask`.

## Testing Guidelines

There is no formal pytest suite yet. Validate ML changes by running `python ml/nilm_pipeline.py` with the required CSVs in `data/`, then compare accuracy, macro-F1, reports, and generated files in `results/`. For cloud changes, run `python test_azure_connection.py` with a local `.env` based on `.env.example`. For firmware feature consistency, flash `nilm_validate_features.c` and compare the JSON dump with `compare_nilm_features.py`. Do not commit credentials or generated artifacts.

## Commit & Pull Request Guidelines

Recent commits use short imperative summaries, for example `readme updated` and `Refactored ml pipeline and added the firmware with updated readme`. Keep commits focused and mention the affected area when useful, such as `ml: adjust cross-session feature selection`. Pull requests should describe the behavior change, list commands run, note dataset assumptions, and include screenshots or plots when evaluation output changes.

## Model Architecture & Training Details

### Feature set (20 features)

The winning CV variant is **"No temp or accel FFT"** — 20 features, no temperature or FFT bins:

| Series | Features | Source column | Units |
|--------|----------|---------------|-------|
| Current | `cur_mean`, `cur_std`, `cur_min`, `cur_max`, `cur_range`, `cur_rms`, `cur_p25`, `cur_p75`, `cur_iqr` | `ina_a_ma` | mA |
| Power | `pwr_mean`, `pwr_std`, `pwr_range` | `ina_a_mw` | mW |
| Accel X | `accel_x_std`, `accel_x_range` | `accel_x` | m/s² |
| Accel Y | `accel_y_std`, `accel_y_range` | `accel_y` | m/s² |
| Accel Z | `accel_z_std`, `accel_z_range` | `accel_z` | m/s² |
| Accel RMS | `accel_rms_mean`, `accel_rms_std` | `accel_rms` | m/s² |

### Sensors used for training

**INA219-A only.** INA219-B (`ina_b_ma`, `ina_b_mw`), `motor_rpm`, and temperature columns (`ntc_c`, `tmp117_c`) are explicitly dropped at data-load time (line 120 of `nilm_pipeline.py`). The winning variant also drops FFT features. Raw CSVs have 13 columns but the model sees only 20 derived window statistics from 6 raw series: `ina_a_ma`, `ina_a_mw`, `accel_x`, `accel_y`, `accel_z`, `accel_rms`.

### Sampling & windowing

- Sample rate: 100 Hz (10 ms tick on both firmware and training data collection)
- Window: 128 samples (1.28 s), step 64 (50% overlap)
- Dead-current filter: rows with `|ina_a_ma| < 2.0 mA` are dropped before windowing
- Train/test split: 80/20 chronological (not random) with 128-sample purge gap
- CV: 5-fold purged blocked cross-validation

### Model

- Random Forest: 200 trees, max_depth=12, min_samples_leaf=5, class_weight="balanced"
- 4 classes: unloaded (1), light_load (2), heavy_load (3), stall (4)
- Prediction: soft voting (average per-tree class probabilities, pick max)
- Export: `export_random_forest_firmware()` walks each tree and writes flat C arrays

### Training data

Four Session-A files (in `data/`):
- `class1_unloaded__1_.csv` — label 1 (~295K rows)
- `class2_light_load__1_.csv` — label 2 (~185K rows, timestamp-reset → largest contiguous segment extracted)
- `class3_heavy_load__1_.csv` — label 3 (~136K rows)
- `class4_stall.csv` — label 4 (~149K rows)

All collected at **150 RPM** with Adafruit sensor libraries (m/s² acceleration, mA/mW from INA219 power register).

## Deployment Consistency: Fixed Mismatches

The following mismatches between training and `esp32_telemetry.c` were identified in an audit and fixed:

| # | Issue | Fix applied | Location |
|---|-------|-------------|----------|
| 1 | Accel in **g** (ESP32) vs **m/s²** (training) | Multiply raw ADXL345 reads by `9.81f` | `adxl345_read_raw()` |
| 2 | Rolling Z−1g vibration RMS vs instantaneous `√(ax²+ay²+az²)` | Replace rolling buffer with per-sample RMS | `vSensorTask()` |
| 3 | `current × 12.0V` fixed-nominal power vs INA219 power register | Read register 0x03 (`ina219_read_power_mw()`), Cal=4096 → 2 mW/LSB | `ina219_init_one()`, `ml_infer_window()` |
| 4 | `max(abs(phase_a), abs(phase_b))` current vs INA219-A only | `f.current = fabsf(phase_a_current)` | `vSensorTask()` |
| 5 | 600 RPM vs 150 RPM training data | `MOTOR_TARGET_RPM = 150.0f` | Config section |
| 6 | No dead-current filter vs `|ina_a_ma| >= 2.0 mA` training filter | Skip `nilm_window_add()` when `|ina_a_ma| < 2.0` | `ml_infer_window()` |

## C Export Bug: Invalid Float Literals

**Root cause:** `_format_float()` in `nilm_pipeline.py` used Python's `:.9g` format specifier, which strips the decimal point for whole-number floats — producing `0f`, `1f`, `-2f` instead of valid `0.0f`, `1.0f`, `-2.0f`.

**Fix:** Insert `.0` before `f` suffix when formatted string lacks a decimal point:

```python
def _format_float(value):
    if not np.isfinite(value):
        return "0.0f"
    s = f"{float(value):.9g}"
    if "." not in s:
        s += ".0"
    return s + "f"
```

Regenerate with `python ml/nilm_pipeline.py` — the export runs at end of `main()`. Verify no broken literals remain with `gcc -fsyntax-only -std=c11 firmware/nilm_model.c`.

## Firmware: Two Separate Paths

**Data collection** (`iot_testbed/`): Arduino sketch using Adafruit libraries, streams CSV at 100 Hz, motor at 150 RPM, INA219-B hardcoded to 0.00. This produced the training data.

**Production** (`esp32_telemetry.c`): ESP-IDF FreeRTOS, bare I2C sensor drivers (no Adafruit libs), NILM inference at 100 Hz, Azure IoT Hub MQTT. Runs the exported 200-tree Random Forest. Motor defaults to 150 RPM to match training. Sensor addresses: ADXL345 (0x53), TMP117 (0x48), INA219A (0x40), INA219B (0x41).

## Key Architectural Decisions

- Training labels are **hardcoded per file**, not read from the CSV `load_class` column
- Feature extraction in C is **name-based** (`nilm_feature_value()` parses feature names to dispatch series + statistic) — a different winning variant only requires regenerating `nilm_model.c`, no firmware code changes
- The Python pipeline's `extract_window_features()` and the C firmware's `nilm_feature_value()` must stay in sync; `nilm_validate_features.c` + `compare_nilm_features.py` exist to verify this
- INA219-B is initialised in firmware (I2C 0x41) for diagnostics (`phase_b_current` in Azure telemetry), but not used for ML features
