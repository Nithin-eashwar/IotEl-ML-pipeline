# Repository Guidelines

## Project Structure & Module Organization

This repository contains a NILM motor-load classifier and related ESP32 firmware.

- `ml/nilm_pipeline.py`: main Python ML pipeline for loading CSV data, extracting window features, training, evaluating, and writing `ml/model.pkl`.
- `ml/compare_nilm_features.py`: Python comparator — reads an ESP32 JSON window dump and recomputes all 20 features independently.
- `single.py`: standalone Python workflow used alongside the main pipeline.
- `test_azure_connection.py`: Azure IoT Hub connection diagnostic.
- `firmware/motor_telemetry/`: ESP-IDF v6 production firmware project (FreeRTOS tasks, sensor drivers, NILM inference, Azure IoT Hub MQTT, three-layer reconnection). Main source: `main/motor_telemetry.c`.
- `firmware/legacy/esp32_telemetry.c`: legacy ESP-IDF firmware (superseded by `motor_telemetry/`).
- `firmware/nilm_validate_features.c`: standalone ESP32 test firmware — captures one 128-sample window and dumps raw samples + 20 computed features as JSON for desktop comparison.
- `firmware/nilm_model.h` / `firmware/nilm_model.c`: generated C Random Forest export (auto-generated by `export_random_forest_firmware()`).
- `firmware/iot_testbed/`: active Arduino sketch for 100 Hz sensor capture and CSV streaming.
- `firmware/legacy/`: modular ESP32/FreeRTOS firmware with sensor, motor, NILM, calibration, and MQTT components.
- `docs/` and `NILM_Cross_Session_Report.md`: design notes and evaluation report.
- `data/`, `results/`, `*.csv`, `*.png`, `*.pkl`, and `.env` are generated or local-only and must not be committed.

## Coding Style & Naming Conventions

Use Python 3.10+ with 4-space indentation, `snake_case` functions and variables, and uppercase constants for pipeline configuration such as `WINDOW_SIZE` and `DATA_DIR`. Keep data-loading, feature-extraction, and evaluation logic separated. Firmware uses C with `.h`/`.c` modules, uppercase `#define` constants, and clear task names such as `vMotorTask` and `vSensorTask`.

## Testing Guidelines

There is no formal pytest suite yet. Validate ML changes by running `python ml/nilm_pipeline.py` with the required CSVs in `data/`, then compare accuracy, macro-F1, reports, and generated files in `results/`. For cloud changes, run `python test_azure_connection.py` with a local `.env` based on `.env.example`. For firmware feature consistency, flash `nilm_validate_features.c` and compare the JSON dump with `compare_nilm_features.py`. Do not commit credentials or generated artifacts.

## Commit & Pull Request Guidelines

Recent commits use short imperative summaries, for example `readme updated` and `Refactored ml pipeline and added the firmware with updated readme`. Keep commits focused and mention the affected area when useful, such as `ml: adjust cross-session feature selection`. Pull requests should describe the behavior change, list commands run, note dataset assumptions, and include screenshots or plots when evaluation output changes.

## Model Architecture & Training Details

### Feature set (20 features)

The winning CV variant is **"No temp or accel FFT"** — 20 features, no temperature or FFT bins:

| Series | Features | Source column | Units |
|--------|----------|---------------|-------|
| Current | `cur_mean`, `cur_std`, `cur_min`, `cur_max`, `cur_range`, `cur_rms`, `cur_p25`, `cur_p75`, `cur_iqr` | `ina_a_ma` | mA |
| Power | `pwr_mean`, `pwr_std`, `pwr_range` | `ina_a_mw` | mW |
| Accel X | `accel_x_std`, `accel_x_range` | `accel_x` | m/s² |
| Accel Y | `accel_y_std`, `accel_y_range` | `accel_y` | m/s² |
| Accel Z | `accel_z_std`, `accel_z_range` | `accel_z` | m/s² |
| Accel RMS | `accel_rms_mean`, `accel_rms_std` | `accel_rms` | m/s² |

### Sensors used for training

**INA219-A only.** INA219-B (`ina_b_ma`, `ina_b_mw`), `motor_rpm`, and temperature columns (`ntc_c`, `tmp117_c`) are explicitly dropped at data-load time (line 120 of `nilm_pipeline.py`). The winning variant also drops FFT features. Raw CSVs have 13 columns but the model sees only 20 derived window statistics from 6 raw series: `ina_a_ma`, `ina_a_mw`, `accel_x`, `accel_y`, `accel_z`, `accel_rms`.

### Sampling & windowing

- Sample rate: 100 Hz (10 ms tick on both firmware and training data collection)
- Window: 128 samples (1.28 s), step 64 (50% overlap)
- Dead-current filter: rows with `|ina_a_ma| < 2.0 mA` are dropped before windowing
- Train/test split: 80/20 chronological (not random) with 128-sample purge gap
- CV: 5-fold purged blocked cross-validation

### Model

- Random Forest: 200 trees, max_depth=12, min_samples_leaf=5, class_weight="balanced"
- 4 classes: unloaded (1), light_load (2), heavy_load (3), stall (4)
- Prediction: soft voting (average per-tree class probabilities, pick max)
- Export: `export_random_forest_firmware()` walks each tree and writes flat C arrays

### Training data

Four Session-A files (in `data/`):
- `class1_unloaded__1_.csv` — label 1 (~295K rows)
- `class2_light_load__1_.csv` — label 2 (~185K rows, timestamp-reset → largest contiguous segment extracted)
- `class3_heavy_load__1_.csv` — label 3 (~136K rows)
- `class4_stall.csv` — label 4 (~149K rows)

All collected at **150 RPM** with Adafruit sensor libraries (m/s² acceleration, mA/mW from INA219 power register).

## Deployment Consistency: Fixed Mismatches

The following mismatches between training and `esp32_telemetry.c` were identified in an audit and fixed:

| # | Issue | Fix applied | Location |
|---|-------|-------------|----------|
| 1 | Accel in **g** (ESP32) vs **m/s²** (training) | Multiply raw ADXL345 reads by `9.81f` | `adxl345_read_raw()` |
| 2 | Rolling Z−1g vibration RMS vs instantaneous `√(ax²+ay²+az²)` | Replace rolling buffer with per-sample RMS | `vSensorTask()` |
| 3 | `current × 12.0V` fixed-nominal power vs INA219 power register | Read register 0x03 (`ina219_read_power_mw()`), Cal=4096 → 2 mW/LSB | `ina219_init_one()`, `ml_infer_window()` |
| 4 | `max(abs(phase_a), abs(phase_b))` current vs INA219-A only | `f.current = fabsf(phase_a_current)` | `vSensorTask()` |
| 5 | 600 RPM vs 150 RPM training data | `MOTOR_TARGET_RPM = 150.0f` | Config section |
| 6 | No dead-current filter vs `|ina_a_ma| >= 2.0 mA` training filter | Skip `nilm_window_add()` when `|ina_a_ma| < 2.0` | `ml_infer_window()` |

## C Export Bug: Invalid Float Literals

**Root cause:** `_format_float()` in `nilm_pipeline.py` used Python's `:.9g` format specifier, which strips the decimal point for whole-number floats — producing `0f`, `1f`, `-2f` instead of valid `0.0f`, `1.0f`, `-2.0f`.

**Fix:** Insert `.0` before `f` suffix when formatted string lacks a decimal point:

```python
def _format_float(value):
    if not np.isfinite(value):
        return "0.0f"
    s = f"{float(value):.9g}"
    if "." not in s:
        s += ".0"
    return s + "f"
```

Regenerate with `python ml/nilm_pipeline.py` — the export runs at end of `main()`. Verify no broken literals remain with `gcc -fsyntax-only -std=c11 firmware/nilm_model.c`.

## Firmware: Two Separate Paths

**Data collection** (`iot_testbed/`): Arduino sketch using Adafruit libraries, streams CSV at 100 Hz, motor at 150 RPM, INA219-B hardcoded to 0.00. This produced the training data.

**Production** (`motor_telemetry.c`): ESP-IDF FreeRTOS, bare I2C sensor drivers (no Adafruit libs), NILM inference at 100 Hz, Azure IoT Hub MQTT, three-layer reconnection. Runs the exported 200-tree Random Forest. Motor defaults to 150 RPM to match training. Sensor addresses: ADXL345 (0x53), TMP117 (0x48), INA219A (0x40), INA219B (0x41).

## Key Architectural Decisions

- Training labels are **hardcoded per file**, not read from the CSV `load_class` column
- Feature extraction in C is **name-based** (`nilm_feature_value()` parses feature names to dispatch series + statistic) — a different winning variant only requires regenerating `nilm_model.c`, no firmware code changes
- The Python pipeline's `extract_window_features()` and the C firmware's `nilm_feature_value()` must stay in sync; `nilm_validate_features.c` + `compare_nilm_features.py` exist to verify this
- INA219-B is initialised in firmware (I2C 0x41) for diagnostics (`phase_b_current` in Azure telemetry), but not used for ML features

## ESP-IDF v6: Driver API Changes

The firmware was migrated from IDF 4.x/5.x legacy APIs to IDF 6.x. Three driver subsystems changed:

### I2C — `driver/i2c.h` → `driver/i2c_master.h`

Old legacy API (removed in IDF 6):
```c
#include "driver/i2c.h"
i2c_config_t conf = { .mode = I2C_MODE_MASTER, ... };
i2c_param_config(I2C_NUM_0, &conf);
i2c_driver_install(I2C_NUM_0, conf.mode, 0, 0, 0);
i2c_master_write_to_device(I2C_NUM_0, addr, buf, len, ticks);
```

New master API:
```c
#include "driver/i2c_master.h"
static i2c_master_bus_handle_t g_i2c_bus = NULL;

i2c_master_bus_config_t cfg = {
    .clk_source = I2C_CLK_SRC_DEFAULT,
    .i2c_port   = I2C_MASTER_PORT,
    .scl_io_num = I2C_MASTER_SCL,
    .sda_io_num = I2C_MASTER_SDA,
    .glitch_ignore_cnt = 7,
    .flags.enable_internal_pullup = true,
};
i2c_new_master_bus(&cfg, &g_i2c_bus);

// Each transfer: add device → transmit → remove device
i2c_device_config_t dev_cfg = {
    .dev_addr_length = I2C_ADDR_BIT_LEN_7,
    .device_address  = addr,
    .scl_speed_hz    = I2C_MASTER_FREQ,
};
i2c_master_dev_handle_t dev;
i2c_master_bus_add_device(g_i2c_bus, &dev_cfg, &dev);
i2c_master_transmit(dev, buf, len, 100);            // write
i2c_master_transmit_receive(dev, &reg, 1, dst, len, 100);  // write-then-read
i2c_master_bus_rm_device(dev);
```

### ADC — `driver/adc.h` → `esp_adc/adc_oneshot.h`

Old (removed):
```c
adc1_config_width(ADC_WIDTH_BIT_12);
adc1_config_channel_atten(ADC1_CHANNEL_6, ADC_ATTEN_DB_11);
int raw = adc1_get_raw(ADC1_CHANNEL_6);
```

New oneshot API:
```c
#include "esp_adc/adc_oneshot.h"
static adc_oneshot_unit_handle_t g_adc_handle = NULL;

adc_oneshot_unit_init_cfg_t unit_cfg = { .unit_id = ADC_UNIT_1 };
adc_oneshot_new_unit(&unit_cfg, &g_adc_handle);

adc_oneshot_chan_cfg_t chan_cfg = {
    .bitwidth = ADC_BITWIDTH_12,
    .atten    = ADC_ATTEN_DB_12,         // renamed from DB_11
};
adc_oneshot_config_channel(g_adc_handle, ADC_CHANNEL_6, &chan_cfg);
adc_oneshot_read(g_adc_handle, ADC_CHANNEL_6, &raw);       // was ADC1_CHANNEL_6
```

### MQTT — `esp_mqtt_client_config_t` struct changes (IDF 5.3+)

- `client_id` moved from `credentials.authentication.client_id` to `credentials.client_id`
- `esp_mqtt_client_set_config()` renamed to `esp_mqtt_set_config()`
- `ESP_ERR_MQTT_ALREADY_CONNECTED` removed — check only `ESP_OK`
- `esp_mqtt_set_config()` is called every loop iteration to push the latest SAS token as `credentials.authentication.password`

## Reconnection Architecture

The firmware has a **three-layer** reconnection system: WiFi, MQTT, and a hardware watchdog task. Every layer uses exponential backoff, reason‑code awareness, and a stuck‑counter that triggers `esp_restart()`.

### Layer 1: WiFi (`wifi_event_handler`)

| Disconnect Reason | Behavior |
|---|---|
| `WIFI_REASON_AUTH_FAIL` | Log permanent failure, **return** — no retry |
| `WIFI_REASON_NO_AP_FOUND` | Log permanent failure, **return** — no retry |
| `WIFI_REASON_ASSOC_LEAVE` | Log permanent failure, **return** — no retry |
| All other reasons | Exponential backoff: `delay = MIN(1000 << counter, 60000) ms`, counter capped at 12 |

- `s_wifi_retry` counter reset to 0 on `IP_EVENT_STA_GOT_IP`
- Event handler calls `vTaskDelay()` directly (blocks the event loop briefly — acceptable for this application)

### Layer 2: MQTT (`vAzureTask`)

- `disable_auto_reconnect = true` — ESP-MQTT no longer retries internally; `vAzureTask` owns reconnection

**Start backoff:** Before calling `esp_mqtt_client_start()`, the task delays by `MIN(1000 << s_mqtt_retry, 60000)` ms. Counter capped at 12, reset on successful start.

**Publish fail counting:** `s_pub_fails` increments on every failed `esp_mqtt_client_publish()`. At `MQTT_MAX_FAILS` (5):
- `s_stuck_counter` is set to `STUCK_LIMIT` (10), triggering an immediate watchdog restart
- Client is stopped via `esp_mqtt_client_stop()`; `g_connected` set to `false`

**Recovery cycle:** Every 500 ms loop iteration:
1. Copy fresh SAS token from `sas_refresh_task`
2. Call `esp_mqtt_set_config()` with the latest password
3. If `!g_connected`: apply backoff delay, call `esp_mqtt_client_start()`
4. If `g_connected`: try `esp_mqtt_client_publish()` every 5 s

### Layer 3: Watchdog (`vWatchdogTask`)

```c
static void vWatchdogTask(void *pv)
{
    esp_task_wdt_add(NULL);  // subscribe this task to the TWDT

    while (1) {
        if (g_sas_valid && g_connected) {
            s_stuck_counter = 0;
            esp_task_wdt_reset();       // feed the hardware watchdog
        } else {
            s_stuck_counter++;
        }
        if (s_stuck_counter >= STUCK_LIMIT) {  // 10 consecutive failures = ~5 min
            esp_restart();
        }
        vTaskDelay(pdMS_TO_TICKS(30000));
    }
}
```

| Parameter | Value |
|---|---|
| Check interval | 30 s |
| `STUCK_LIMIT` | 10 (~5 min of consecutive failures) |
| TWDT timeout | 60 s (panic on expiry — catches watchdog task hangs) |
| Healthy condition | `g_sas_valid && g_connected` |
| Reset trigger | `s_stuck_counter >= STUCK_LIMIT` → `esp_restart()` |

### Globals Summary

| Variable | Type | Purpose |
|---|---|---|
| `s_wifi_retry` | `uint32_t` | WiFi backoff exponent, capped at 12 |
| `s_mqtt_retry` | `uint32_t` | MQTT start backoff exponent, capped at 12 |
| `s_pub_fails` | `uint8_t` | Consecutive publish failures, reset on success |
| `s_stuck_counter` | `volatile uint8_t` | Watchdog stuck count, incremented when unhealthy |
| `g_connected` | `volatile bool` | File-scope MQTT connected flag, read by watchdog |

## Azure IoT Hub Connectivity: Issues Fixed & Lessons

These are the bug fixes that got the firmware from TLS connection failures to successful Azure telemetry.

### 1. TLS verification — use certificate bundle, not skip_cert_common_name_check

**Symptom:** `ESP_ERR_MBEDTLS_SSL_SETUP_FAILED`, "No server verification option set"

**Wrong fix (do not use):** `.broker.verification.skip_cert_common_name_check = true` — this bypasses certificate verification entirely, making the connection MITM-able. It also only works because ESP-MQTT's wrapper treats "any field set under verification" as authmode=optional without a CA cert.

**Correct fix:**
```c
#include "esp_crt_bundle.h"
// in both esp_mqtt_client_config_t and esp_mqtt_set_config():
.broker.verification.crt_bundle_attach = esp_crt_bundle_attach,
```

**Prerequisites (already set in sdkconfig):**
```
CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y
CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_DEFAULT_FULL=y
```

The full default bundle includes DigiCert Global Root G2 — Azure IoT Hub's CA. No PEM files needed. No sdkconfig changes needed.

**Why skip_cert_common_name_check appeared to work:** It's not a verification method — it only relaxes CN matching when a cert IS being validated. ESP-TLS v6 sees any field set in `verification` and selects `MBEDTLS_SSL_VERIFY_OPTIONAL` with no CA cert, which means "encrypt but don't verify." This is dangerous. `crt_bundle_attach` is the proper verification method.

### 2. SAS token — sign the full resource URI, correct field order

**Symptom:** Azure returns 401 Unauthorized despite correct device key

**Wrong:** Signing only the hostname (`motor-predictor-hub.azure-devices.net`) and using `sr=` first in the token.

**Correct:**
```c
// String-to-sign = URL_ENCODED(host/devices/deviceid) + "\n" + expiry
char resource_uri[256];
snprintf(resource_uri, sizeof(resource_uri), "%s/devices/%s",
         IOT_HUB_HOST, DEVICE_ID);

// Token = SharedAccessSignature sig=SIG&se=EXPIRY&sr=RESOURCE
snprintf(token_buf, buf_len,
    "SharedAccessSignature sig=%s&se=%" PRIu64 "&sr=%s",
    sig_enc, (uint64_t)expiry, url_resource);
```

Azure IoT Hub requires the HMAC to be computed over `{url-encoded-resource}\n{expiry}` where resource = `{hub}/devices/{device}`. The token field order must be `sig=`, `se=`, `sr=`.

### 3. MQTT client handle — destroy and recreate on reconnect

**Symptom:** `ESP_ERR_INVALID_STATE` when calling `esp_mqtt_client_start()` on a previously failed handle

**Fix:** Before retrying start after a failure:
```c
if (g_mqtt_client != NULL) {
    esp_mqtt_client_stop(g_mqtt_client);
    esp_mqtt_client_destroy(g_mqtt_client);
    g_mqtt_client = NULL;
}
g_mqtt_client = esp_mqtt_client_init(&cfg);   // fresh handle
esp_mqtt_client_register_event(...);           // re-register event handler
esp_mqtt_client_start(g_mqtt_client);          // now it works
```

ESP-MQTT v6 uses internal state machines — reuse after a tear-down is not guaranteed.

### 4. NTP — use callback, not polling sntp_get_sync_status()

**Symptom:** `sntp_get_sync_status()` returned `SNTP_SYNC_STATUS_RESET` indefinitely

**Fix:** Register a time-sync notification callback instead of busy-polling:
```c
static volatile bool g_ntp_synced = false;

static void sntp_sync_cb(struct timeval *tv) {
    g_ntp_synced = true;
}

// In app_main:
vTaskDelay(pdMS_TO_TICKS(2000));   // settle delay
esp_sntp_set_time_sync_notification_cb(sntp_sync_cb);
// Use two servers for reliability
esp_sntp_setservername(0, "time.google.com");
esp_sntp_setservername(1, "pool.ntp.org");
esp_sntp_init();
for (int retry = 0; !g_ntp_synced && retry < 60; retry++)
    vTaskDelay(pdMS_TO_TICKS(1000));
```

### 5. Epoch guard — prevent SAS generation before NTP sync

**Symptom:** SAS tokens generated with epoch 0 or bogus time are rejected by Azure (but the real diagnostic signal is the NTP callback fix above)

**Fix:** Guard `generate_sas_token()`:
```c
#define MIN_VALID_EPOCH 1704067200ULL  /* Jan 1 2024 */
if ((uint64_t)time(NULL) < MIN_VALID_EPOCH) {
    return false;  // clock not synced
}
```

### 6. Component dependencies — espressif__mqtt, esp_task_wdt, and idf_component.yml

**Lessons:**
- `espressif__mqtt` must be declared in `main/CMakeLists.txt` REQUIRES AND fetchable via `idf_component.yml` (add `espressif/mqtt: "^1.1.0"` under dependencies)
- `esp_task_wdt` is NOT a standalone component in IDF v6 — it's built into `freertos`. Remove it from REQUIRES.
- `esp_task_wdt_init()` does NOT exist in IDF v6 — use `esp_task_wdt_reconfigure()` instead

### 7. Build-time secrets — inject via CMake, never hardcode

**Principle:** Credentials (WiFi SSID/pass, IoT Hub host, device ID, primary key) must never be committed. Use CMake `add_definitions(-DVAR="$ENV{VAR}")` to inject them from host environment at build time.

**Setup:**
1. `.env` file in project root (gitignored): `export WIFI_SSID="..."` etc.
2. `main/CMakeLists.txt` reads `$ENV{...}` → `add_definitions(-DMACRO="value")`
3. `build.sh` wrapper: `source .env && docker run ... -e VAR ... idf.py "$@"`

### Future Coding Guidelines for This Project

1. **Never** commit credentials — always use CMake env injection + `.env` + `.gitignore`
2. **Never** use `skip_cert_common_name_check` — use the x509 cert bundle (`esp_crt_bundle_attach`)
3. **Always** destroy and recreate MQTT client handles on reconnect — don't reuse after failure
4. **Always** use SNTP callback for time sync — polling `sntp_get_sync_status()` is unreliable
5. **Always** guard SAS generation with a minimum epoch check
6. **Check** `idf_component.yml` when adding a managed component — REQUIRES alone isn't enough
7. **Check** component names against IDF v6 API — `esp_task_wdt` doesn't exist as a standalone component, `ADC_ATTEN_DB_11` was renamed to `DB_12`, `ADC1_CHANNEL_6` → `ADC_CHANNEL_6`
